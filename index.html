THE PROBLEM

Cloud systems are big, complex, and easy to attack

A huge attack surface

Networks, APIs, virtual machines and hardware all mix together. Standard protocols and virtualization open many doors.

DoS is a top threat

SYN floods, slow HTTP requests, memory contention: they all try to knock a service offline.

Reacting is too late

Classic tools wait for the attack, then respond. By then, users already feel the damage.

Goal: act before or during an attack, not after. That is “proactive defense.”

THREAT MODEL

Who is the attacker?

The attacker can

  • Launch SYN flooding, SlowHTTP and Memory DoS attacks
  • Send bad traffic or fight for shared resources
  • Change tactics over time

The attacker cannot

  • Get admin access to the cloud
  • Touch or tamper with the defense system

Key assumption: the cloud’s monitoring and management tools can be trusted.

ARCHITECTURE

LLM-PD: five agents in a closed loop

(a)

Collector

Gathers data and cleans it up

(b)

Analyzer

Checks system status and scores the risk

(c)

Decision-Maker

Breaks the task down and picks actions

(d)

Deployer

Runs a known fix or writes a new script

(e)

Feedback Giver

Checks results and updates memory

Memory: what worked, what failed, and why

Each agent is a prompted LLM. One full pass through all five = one “round.”

Ruilin Gao · LLM-PD (arXiv:2412.21051)

STAGES (A) AND (B)

First collect the data, then score the risk

(A) COLLECTOR

  • Pulls traffic, logs, metrics, events and configs
  • Parses, removes duplicates, merges repeats
  • Outputs one clean JSON for the next agent

Example from the paper:

2× failed_login, admin, 192.168.1.10
1× heartbeat, ok
→ 1 alert: repeated failed logins
→ heartbeat dropped as noise

(B) ANALYZER

Gives a risk score from three parts:

Scope 0–3

+

Impact 0–4

+

Duration 0–3

→ scaled to a 0–10 risk score, used to rank what to fix first.

  • The LLM explains cause and effect, not just a label
  • Flags strange patterns it has never seen before

Ruilin Gao · LLM-PD (arXiv:2412.21051)

STAGES (C) AND (D)

Plan the defense, then put it in place

(C) DECISION-MAKER

  • Splits a big task into ordered subtasks, ranked by risk
  • Checks every action: bad values or broken limits are rejected
  • Exploration rate: mostly reuse what worked, sometimes try something new
  • A solver balances goals like security, cost and speed

Why all the checks? To stop LLM hallucinations from reaching the real system.

(D) DEPLOYER

  1. Look in the defense library first
  2. Not there? The LLM writes a new script
  3. Check it: syntax, static analysis, sandbox run
  4. Deploy it, then save it to the library

Example from the paper (simplified):

#!/bin/bash
IP="192.168.1.10"
iptables -A INPUT -s $IP -j DROP
echo "$(date): blocked $IP" >> /var/log/defense.log

Ruilin Gao · LLM-PD (arXiv:2412.21051)

STAGE (E)

Learn from every round, without retraining

1. Score the result

Five views: security, recovery time, resources, money cost, and service quality (QoS). Weights depend on the situation.

2. Decide if it’s done

After each action, check for success or failure. Tag the whole action sequence with the outcome.

3. Remember it

Short-term: each step in this episode.
Long-term: a sliding window of recent full episodes.

Memory goes back into the prompts: repeat what worked, avoid what failed — and keep the prompt short.

Ruilin Gao · LLM-PD (arXiv:2412.21051)

CASE STUDY

How they tested it

3 LLMs

GPT-4o mini
DeepSeek-R1-Distill-Qwen-32B
Qwen3-32B

3 DoS attacks

SYN flooding and SlowHTTP (2 attacker IPs)
Memory DoS (attacker VMs on the same machine)

Simulated cloud

Up to 10 service replicas, 100 pods, 256 connections per pod
5 racks × 10 machines × 10 VMs

Baselines and runs

Deep RL: DQN, Actor-Critic, PPO
1 step = 30 s · 200 tests × 10 episodes

Note: everything runs in a simulation, not on a real cloud.

DISCUSSION

What I liked, and what I would question

Strengths

  • Covers the full loop, not just one task
  • Works with any LLM; you can swap models per stage
  • Learns from memory, no retraining
  • Safety checks on every action and script
  • Code is open source

Open questions

  • Only simulated attacks: no real cloud or real traffic
  • Seconds of delay vs. floods that hit in milliseconds
  • Logs go straight into prompts: risk of prompt injection?
  • Auto-running LLM-written scripts: is a sandbox enough?
  • No ablation of memory; only deep RL baselines

Ruilin Gao · LLM-PD (arXiv:2412.21051)

TAKEAWAYS

Three things to remember

1

LLM agents can cover the full defense loop: sense, assess, decide, act, and learn.

2

Memory feedback lets the system improve without retraining — and it beat deep RL on all three DoS attacks.

3

The open problems are speed, the safety of AI-written actions, and testing in the real world.
